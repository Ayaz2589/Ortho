# SimpleFIN Bank-Sync — Developer Guide

**Read this when:** working on bank connections or transaction sync — extending the
SimpleFIN integration, adding a third provider, or building features on top of synced
transactions. SimpleFIN is Ortho's **go-forward** bank-data provider (spec 028); Plaid
(spec 024) is **contained** under `deprecated/` namespaces but kept fully wired as a
rollback path.

Grounded in the competitive research at
[`./research/competetive-analysis/simplefin-developer-analysis.md`](./research/competetive-analysis/simplefin-developer-analysis.md)
and the spec at [`../specs/028-simplefin-sync/`](../specs/028-simplefin-sync/).

## 1. What SimpleFIN is (30-second version)

SimpleFIN is a tiny, **read-only** protocol. The member does the bank sign-in on
**SimpleFIN Bridge** (a hosted implementation, MX upstream) and comes back with a
one-time **setup token**. Ortho claims that token server-side and receives an **Access
URL** with embedded HTTP Basic-Auth — the standing, read-only credential. There is **no
OAuth widget, no webhooks, no hand-back plumbing** — a token paste that works identically
on web and the iOS shell. All bank data comes from one endpoint: `GET {ACCESS_URL}/accounts`.

Contrast with Plaid: Plaid needed Link (embedded/hosted), a public-token exchange, a
session table, an OAuth return route, and an iOS custom-scheme hand-back. SimpleFIN needs
none of that.

`_shared` copy; edit `src/` and re-sync.

## 3. The token flow (claim)

```
setupToken ──base64 decode──► claimURL ──POST──► accessURL   (token now consumed, single-use)
                                                    │
                    complete_simplefin_link RPC: Vault secret + institution row (ATOMIC)
                                                    │
                    best-effort GET /accounts?balances-only=1 → linked_accounts
```

- **Reliability**: the setup token is single-use — the POST consumes it and returns the
  Access URL exactly once. So storing the Access URL in Vault is the first durable action.
  If the client loses the response, the connection already exists server-side and shows up
  on the next Linked-banks load; the consumed token cannot (and need not) be re-claimed.
- **Institution identity**: `provider_item_id = deriveProviderItemId(accessUrl)` =
  `'sfin_' + hash(accessUrl)[:32]` — a stable, opaque, non-secret id anchoring the
  `UNIQUE(provider, provider_item_id)` idempotency. The real Access URL lives **only** in
  Vault (`store_institution_secret`, the provider-agnostic wrapper reused from spec 024).
- One claimed Access URL = one `linked_institutions` row, even if `/accounts` spans several
  banks; each account's bank name is stored per `linked_accounts.official_name`.

## 4. The sync loop

```
active simplefin institution
   │  manual? within 1h cooldown ──► rate_limited (calm "just updated")
   ▼
window = buildSyncWindow(last_synced_at, now)   // first: now-90d; else last-3d .. now (≤90d)
   ▼
GET /accounts?start-date&end-date&pending=1  →  parseSimpleFinAccounts
   ▼
for each txn:  toUpsertPayload  →  upsert_transaction(p_tx, p_shares)
   ▼
mark_simplefin_synced(institution, window.end, manual)
```

- **Scheduling** is an operator concern (no CI, no live account): wire a daily trigger
  (Supabase scheduled function / `pg_cron` / external cron) to `POST /functions/v1/simplefin-sync`
  `{ institutionId }` per active institution. Stay within SimpleFIN's ~24 req/day/connection.
- **Manual refresh** ("Refresh now" in Linked banks) is rate-limited to 1/hour per
  connection (`isManualRefreshBlocked`, `last_manual_refresh_at`).

## 5. The money rules (the part to get right)

`normalize.ts` is the safety-critical module — a sign error would swap income and spending.

- **`amount` is a signed decimal STRING** (e.g. `"-33.45"`). `amountToCents` parses it
  **without floating point** (string split, pad/truncate to 2 digits) → `{ amountCents, kind }`.
- **Ortho stores `amount_cents` NON-NEGATIVE**; direction is the `transaction_kind`
  (`income`/`expense`). So the sign becomes the kind: **SimpleFIN positive = inflow →
  `income`; negative → `expense`** (this is the *inverted* convention vs Plaid). There is
  never a negative to store.
- **Dedupe**: `dedupeKey(account, txn) = "simplefin:<account>:<txn>"` (SimpleFIN ids are
  unique only *within* an account, so the account must be in the key). Stored on
  `transactions.source`.
- **Ledger id**: `ledgerId(household, account, txn)` = a deterministic UUID from a 128-bit
  hash. Same (household, account, txn) → same row across every sync, so `upsert_transaction`'s
  `on conflict (id)` makes re-syncs idempotent and **pending→posted an in-place update**.
  Household is in the hash so two households can't collide on one ledger row.
- **Split**: synced rows get one default share = the whole amount to the `household_people`
  person linked to the connector (else the lowest `sort_order` active person), satisfying
  `upsert_transaction`'s shares-sum-equals-total invariant. Members re-split later.
- **Category**: `income → 'income'`; unmatched expense → `'entertainment'` (the CLI import
  engine's documented fallback). Richer merchant-rule categorization is a future enhancement
  (see §8).

## 6. Defensive parsing (schema is version-dependent)

SimpleFIN's published schema differs across protocol versions (v1 nested `org` + `errors`;
v2 `connections` + `errlist`). `parseSimpleFinAccounts` reads **both** tolerantly and never
throws on malformed input; in-band provider errors become `warnings` (surfaced, not fatal).
⚠️ **Before trusting any new field, capture a real sandbox `/accounts` response and pin the
parser against it** — the parser is a map, not the territory.

## 7. Testing & the verify bar

TDD, mocked `fetch` (the `fakeSfinFetch`/`throwingSfinFetch` helpers) — **no live Bridge
account in CI**. To verify end to end:

```bash
cd services/aggregation && npx tsc --noEmit && npm test && npm run sync:functions && npm test
cd web && npx tsc --noEmit && npm test && npm run build
cd supabase/functions && deno check simplefin-*/index.ts && deno test
```

Money/dedupe/normalization live in `test/normalize.test.ts` + `test/simplefin-accounts.test.ts`
(heaviest coverage). Edge-function pure logic is in `simplefin-sync/sync-logic.test.ts`.

## 8. Extending it (future functionality)

- **Live validation**: create a SimpleFIN Bridge account, generate a setup token, run the
  manual quickstart in [`../specs/028-simplefin-sync/quickstart.md`](../specs/028-simplefin-sync/quickstart.md),
  capture the real `/accounts` shape, and reconcile the parser/fixtures.
- **Richer categorization**: run the CLI import engine's `categorize(merchant, kind)` rules
  (`web/scripts/import/engine/categorize.ts`) on synced merchants instead of the flat
  `entertainment` fallback — ideally by lifting those rules into the aggregation core so
  there's one source of truth.
- **Pending→posted with id re-keying**: today a pending txn that keeps the same SimpleFIN id
  updates in place; if a provider re-keys the id on posting, a fuzzy `(account, amount,
  date±)` supersede would avoid a transient duplicate (documented in
  `contracts/accounts-sync-lifecycle.md`, not yet implemented).
- **Owner assignment / multi-currency**: synced rows default to one person and assume USD
  (currency is stored per account for display). Both are deliberate out-of-scope seams.
- **A third provider**: add its value to `linked_provider`, a module in the core ending in
  the same shapes, edge functions, and a branch in the web client — exactly how SimpleFIN
  slotted in behind the seam.
