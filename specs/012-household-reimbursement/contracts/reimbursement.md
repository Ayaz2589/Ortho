# Contract: Household reimbursement & settle-up

Mirrored pure logic (TS ↔ Swift), the golden-vector schema, the transfer data contract, and the UI contract.

## 1. Pure balance function (mirrored, vectored)

### `balanceBetween(viewer, other, transactions) → number` (signed cents)

Positive ⇒ **other owes viewer**; negative ⇒ **viewer owes other**; 0 ⇒ settled.

```
net = 0
for tx in transactions:
  if tx.kind == 'expense' and tx.paid_by != null:
     if tx.paid_by == viewer and other in owners(tx):  net += shares(tx)[other]
     if tx.paid_by == other  and viewer in owners(tx):  net -= shares(tx)[viewer]
  if tx.kind == 'transfer':                 # sender = paid_by, recipient = the single owner
     F = tx.paid_by ; R = owners(tx)[0] ; A = tx.amount_cents
     if F == other  and R == viewer:  net -= A      # they paid you back
     if F == viewer and R == other:   net += A      # you paid them back
return net
```

- Integer cents only (no rounding). `owners(tx)` excludes nobody special; the `paid_by == owner` case naturally contributes 0 for the payer's own share (we only read the *other* party's share).
- web `lib/balances.ts` ↔ iOS `Balances.swift`. Asserted by both suites against `member-balance.json`.
- A convenience `balancesForViewer(viewer, members, transactions)` may map `balanceBetween` over the other members; only `balanceBetween` needs vectoring.

## 2. Golden vector schema — `shared/test-vectors/member-balance.json`

Generated by `web/scripts/gen-vectors.ts`; asserted by web Vitest **and** iOS XCTest.

```jsonc
{
  "cases": [
    {
      "name": "string",
      "viewer": "personId",
      "other": "personId",
      "transactions": [ /* minimal tx: {kind, paid_by, amount_cents, owner_ids, shares} */ ],
      "expected": 5000   // signed cents; + => other owes viewer
    }
    // cases: worked example ($150 split 100/50, you paid → +50);
    //        reverse (other paid → negative);
    //        payer-not-an-owner (other's solo expense you paid → + full amount);
    //        reimbursement zeroes it; partial reimbursement; over-reimbursement (flips sign);
    //        multi-expense net with mixed payers; a 3rd member's tx does not affect viewer↔other.
  ]
}
```

UUID-form person ids so iOS can decode directly. Each test computes `balanceBetween(viewer, other, transactions)` and asserts `=== expected`. No change to existing vector files; `transaction-splits.json` still locks `computeShares`.

## 3. Transfer row data contract (mirror TS ↔ Swift)

- `kind = 'transfer'`, `paid_by = sender`, `owner_ids = [recipient]`, `shares = { recipient: amount_cents }`, `category = 'transfer'`, `amount_cents > 0`, `paid_by != recipient`.
- `paid_by` round-trips through create/update/rehydrate on both surfaces; the rehydrate share-fallback is transfer-aware.
- Filtering/listing learns `transfer` (it appears in the activity list; a kind filter may offer it).

## 4. UI contract (both surfaces)

**Payer picker (expense):** in the add/edit form, a "Paid by" member picker defaulting to the current member; only shown when the household has > 1 member; persists `paid_by`.

**Transfer direction:** a third segment beside Expense/Income whose body is a **From → To** member pair + amount (no category/source/split/merchant rows). Validation: amount > 0, From ≠ To.

**Balance line:** in the transactions/expense section, per other member — "**Tasnuva owes you $50**" / "**You owe Tasnuva $50**" / "**Settled**". Tokens only; **owing is never red** (use `--text`/`--accent`; `--positive` is not used to flag a debt). Tabular money, unabbreviated, Unicode minus if a signed figure is shown.

**Settle up:** a button next to the balance that opens the transfer form pre-filled (From = the ower, To = the payer, amount = the owed amount), editable before saving.

**Activity row/detail:** a transfer renders as a directed "Sender → Recipient $X", visually distinct from expenses/income; the expense detail shows "Paid by <member>".

**Accessibility:** all pickers/buttons are real semantic controls, keyboard-reachable, ≥40px (≥44 touch), focus-visible.

## 5. Aggregate-exclusion contract

No spend/income/budget/insight/per-owner total may include `kind = 'transfer'`. Implemented by the existing `kind === 'expense'`/`'income'` guards; verified by an explicit test that adding a transfer changes none of those figures.
