# Web ↔ iOS functional parity audit — 2026-07-02

Method: 7 area-comparison agents read both implementations side by side; every claimed
divergence was then adversarially verified by an independent agent (76 agents total).
Form-factor adaptations sanctioned by the constitution were classified out, as were
divergences already documented in PARITY.md and the date-handling bugs found earlier
on 2026-07-02 (web TxForm UTC slice, iOS wall-clock dates, daily-expense RPC UTC cast).

**Result: 65 confirmed divergences** (4 high, 33 medium, 28 low), 4 sanctioned as intentional/documented.

Severity: **high** = wrong data/money shown or possible data loss; **medium** = feature or
behavior gap a user would notice; **low** = minor behavioral drift.


## HIGH

### [auth] Web bootstrap ignores Supabase errors during household find-or-create — a transient query failure can silently create a duplicate household

- **web**: supabase-js resolves with `{ data, error }` instead of throwing, and web's bootstrap never checks `error`: the `users` upsert result is discarded (web/lib/store.tsx:223); the `household_members` membership select destructures only `data` (store.tsx:226-230), so on any error `membership` is null and the code takes the "no membership" branch (store.tsx:233/241), inserting a brand-new `households` + `household_members` row (store.tsx:242-248). The outer try/catch (store.tsx:256) only catches genuine throws, which supabase-js query builders don't produce.
- **iOS**: Every bootstrap step throws on failure: `HouseholdsAPI.findOrCreate` propagates errors from the membership select and inserts (iOS/Ortho-iOS/Services/HouseholdsAPI.swift:26-65), and `bootstrapUserSession` catches any throw, sets `bootstrapDidFail`, and stops — it never falls through to the create branch on a failed read (iOS/Ortho-iOS/App/AppState.swift:1159-1206). A transient error yields the Retry screen, not a second household.
- **impact**: If the membership query fails once on web (transient 5xx, RLS hiccup) while the inserts succeed, the user is silently attached to a fresh empty "Home" household; on the next sign-in `.limit(1)` may pick either membership, so their real shared data can appear to vanish. iOS fails safe in the same situation.
- **verification**: Verified on both sides. Web (web/lib/store.tsx): the bootstrap discards the users-upsert result (line 223), destructures only `data` from the household_members select (226-230), and treats `data: null` — which supabase-js v2 returns on ANY query error, since builders resolve {data,error} and never throw without .throwOnError() (zero uses in web/) — as "no membership" (233), falling into the else branch (241-248) that inserts a brand-new households + household_members row (those insert errors are also discarded). The try/catch at 256 cannot catch these. iOS: HouseholdsAPI.findOrCreate (Services/HouseholdsAPI.swift:26-65) uses `try await ... .execute()` throughout, so a failed membership read throws before reaching the create branch; bootstrapUserSession (App/AppState.swift:1159-1206) catches, sets dataError + bootstrapDidFail, and surfaces a Retry screen — it never creates a household after a failed read. Not documented: PARITY.md's "Known divergences → Apps" section (lines 86-107) lists only atomic-write/insights-preview/monthsElapsed; the 2026-06-22 entry even records the iOS bootstrap-recovery screen as an iOS-only fix with no matching web note. Not form-factor. Impact: one transient failure of the membership select on web (with inserts succeeding) persistently attaches the user to a duplicate empty "Home" household; the unordered `.limit(1)` on later sign-ins can pick either membership, making the real shared data appear to vanish. iOS fails safe in the same scenario. Rated high because the triggered outcome is persistent data corruption plus the user's real household data disappearing from view, with no recovery UI on web.

### [crosscutting] Property mortgage/lease/units writes: web ignores every sub-table result (silent data loss possible); iOS fails loudly with local rollback

- **impact**: Editing a property on web during a flaky connection can permanently delete its mortgage/lease/unit data with zero feedback — the housing cards keep rendering the stale optimistic copy until the next reload reveals the loss. The identical failure on iOS shows the error and reverts.
