# Implementation Plan: Transaction Filters (iOS + web)

**Branch**: `006-transaction-filters` | **Date**: 2026-06-15 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/006-transaction-filters/spec.md`

## Summary

Add richer, combinable filters (category, kind, source, owner, month/date-range) to the Transactions page on **both** clients, on top of the existing scope toggle + search. The decision logic is extracted into one **pure function** — `filterTransactions(transactions, criteria, ctx)` — implemented in TypeScript (`web/lib/transactionFilters.ts`) and Swift (`iOS/.../TransactionFilters.swift`), and locked by a **shared golden-vector** file (`shared/test-vectors/transaction-filters.json`) that both the web Vitest parity suite and the iOS XCTest parity suite assert against — the same mechanism already used for mortgage/insights. The web page (compact `page.tsx` + expanded `TransactionsDesktop.tsx`) and the iOS `TransactionsView.swift` are refactored to hold a single `FilterCriteria`, render a filter surface (right **drawer** on web desktop / **bottom sheet** on iOS / panel on web compact), show active-filter chips + a count badge + clear-all, and a distinct "no matches" empty state. Grouping/totals stay in the existing helpers, applied to the filtered list.

## Technical Context

**Storage**: None new. Filtering is in-memory over the already-loaded `transactions` (web store / iOS `appState`).

**Testing**: Web Vitest (`npm test`; pure-logic node + jsdom component suites) incl. a `*.parity.test.ts` against the vectors; iOS XCTest parity test (added to the test target's Copy Bundle Resources, run in Xcode). Vectors generated by `web/scripts/gen-vectors.ts`.

**Target Platform**: iOS app + web (compact 0–639, medium 640–1023, expanded 1024+).

**Project Type**: Cross-platform UI feature with a shared pure-logic core + parity vectors.

**Performance Goals**: Filtering is synchronous over the loaded set (hundreds–low thousands of rows); list updates immediately on any filter change (no fetch, no perceptible delay).

**Constraints**: Identical behavior across clients (vector-locked); design-token styling only; fully keyboard/AA accessible on web, native accessible on iOS; timezone-stable date boundaries; additive (cleared filters = today's behavior).

**Scale/Scope**: One pure module + vectors + generator per platform; filter UI on 3 surfaces (web compact, web desktop, iOS). ~6 dimensions.

**Structure Decision**: The behavior lives in one pure function per platform, vector-locked (SC-002/FR-013/14). The web page logic that today is inline (`inScope`/`matches`/`months` useMemo in `page.tsx`) is refactored to call `filterTransactions`; a `useTransactionFilters` hook holds the criteria + derived option lists so the compact page and the desktop component share state shape and behavior. Grouping/totals remain in `lib/format.ts` applied to the filtered list. iOS mirrors the function and presents a bottom sheet, keeping the existing scope pills + `SearchField`.

## Architecture & Data Flow

```
FilterCriteria { scope, query, categories[], kind, sources[], owners[], dateFrom?, dateTo? }
FilterContext  { householdId, ownerNames: { [userId]: name } }    // serializable → vector-friendly

filterTransactions(transactions, criteria, ctx) -> Transaction[]   // pure; AND across dims, OR within multiselect
   scope(householdId) ∧ search(query over merchant/source/category/ownerNames) ∧
   (categories ∅ ? all : category ∈ categories) ∧ (kind = all ? : tx.kind = kind) ∧
   (sources ∅ ? all : source ∈ sources) ∧ (owners ∅ ? all : owner_ids ∩ owners ≠ ∅) ∧
   (dateFrom ? date ≥ dateFrom) ∧ (dateTo ? date < dateTo)        // [from, to)

UI:  criteria (useTransactionFilters / @State) → filterTransactions → groupByDay → groupDaysByMonth → render
     activeFilterCount(criteria) → badge ; clear-all → emptyCriteria(preserve? no — full reset)
     filtered.length === 0 && hasAnyTransactions → "no matches" state (else existing states)
```

`month` UI control sets `dateFrom = startOfMonth, dateTo = startOfNextMonth`; an explicit range sets both. `monthBounds(yyyymm)` is the single date helper (deterministic, injected "today" only for the default/placeholder).
