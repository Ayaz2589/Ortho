# create-pr skill

Create a GitHub pull request for the current branch using the `gh` CLI. The PR
body is **always** generated by `.claude/scripts/pr-build-body.sh` — never
hand-written — so every PR in this repo has an identical structure.

> **Sandbox note:** inside a Docker Sandbox, prefix every `gh` command with
> `GH_TOKEN=placeholder` (`gh auth status` shows logged-out there, but the proxy
> injects the real token — see root `CLAUDE.md`). On the host, run `gh` bare —
> the placeholder would override real auth. Detect with: `[ -n "$SANDBOX_VM_ID" ]`.

Follow these steps in order:

## 0. Load or initialize config

Check if `.claude/pr-config.md` exists in the project root.

**If it exists:** Read it and extract the saved values (GitHub username, display
name, default base branch, favorite labels).

**If it does NOT exist:** run first-time setup:

1. Get the authenticated GitHub user:
   ```bash
   gh api user --jq '{login: .login, name: .name}'
   ```
2. Detect the default base branch:
   ```bash
   gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name'
   ```
3. Fetch available labels:
   ```bash
   gh label list --json name --jq '.[].name' --limit 50
   ```
4. Ask the user (AskUserQuestion, multiSelect) which labels they commonly use —
   they can pick multiple or none.
5. Save the config to `.claude/pr-config.md`:
   ```markdown
   # PR Config

   ## GitHub User
   - Username: <login>
   - Display Name: <name>

   ## Defaults
   - Base Branch: <branch>
   - Favorite Labels: <comma-separated list or "none">
   ```

Proceed with the saved/discovered values.

## 1. Validate branch state

Run `git status` and `git log --oneline <base-branch>..HEAD` to confirm:
- You are NOT on the base branch
- There are commits to include in the PR

If on the base branch or there are no commits, tell the user and stop. If there
are staged-but-uncommitted changes that clearly belong to this PR, ask the user
whether to commit them first (never commit silently).

## 2. Check remote tracking

Run `git rev-parse --abbrev-ref --symbolic-full-name @{u} 2>/dev/null` to check
if the branch tracks a remote.

- Not tracking → push with `git push -u origin HEAD`
- Tracking → check `git status -sb`; push if ahead.

## 3. Gather PR details

Use AskUserQuestion to ask the user the following (one question block):

**Title:** Suggest a default from the branch name and commits, following this
repo's convention — `type(scope): subject`, e.g. `feat(027): transaction tags &
richer notes`, `docs: full refresh of docs/`, `ci: add deploy-before-migrate
guard`. If the user passed a title as the skill argument, skip this question.

**Assignee:** Options:
- `<saved display name>` (Recommended — uses the saved GitHub username)
- Other (search by username)
- Unassigned

**Labels:** Present the saved favorite labels as recommended options
(multiSelect), plus:
- Other (pick from all repo labels)
- None

## 4. Build the PR body

The body **must** be generated via `.claude/scripts/pr-build-body.sh`. This
locks the structure so every LLM-generated PR has the same shape. If the script
is missing, stop and tell the user — do not improvise a body.

Analyze the commits (`git log --oneline <base-branch>..HEAD`) and diff stat
(`git diff <base-branch>...HEAD --stat`) to draft:
- **1-4 summary bullets** — what the PR does (the *what*, not the *how*)
- **1-5 test-plan steps** the reviewer can follow to verify the change. Prefer
  this repo's real gates: `cd web && npx tsc --noEmit`, `npm test`,
  `npm run gen:vectors` + clean git diff, CI lanes (`web-ci.yml`,
  `capacitor-ios-ci.yml`), `make ingest … DRY_RUN=1`.

Then invoke the script (`--summary`/`--test`/`--breaking`/`--spec`/`--link` are
repeatable; order is preserved):

```bash
BODY=$(.claude/scripts/pr-build-body.sh \
  --summary "<bullet 1>" \
  --summary "<bullet 2>" \
  --test "<test step 1>" \
  --test "<test step 2>" \
  --spec "specs/NNN-feature-dir" \  # optional: the spec this PR implements
  --link "<other linked item>" \    # optional: e.g. "PARITY.md: row added for X"
  --breaking "<note>")              # optional: only for breaking changes
```

Ortho-specific flags to consider every time:
- Implements a Spec Kit feature → `--spec "specs/NNN-…"`.
- Touches money/splits/balances/filters/month-scope logic → the PARITY.md
  reconciliation belongs in the PR: `--link "PARITY.md: <what was reconciled>"`.
- Regenerated vectors → a test step like "review `shared/test-vectors/` diff as
  a behavior change".

The script outputs this canonical structure (sections **never** change; if one
is missing, add a flag to the script — don't append to the body):

```markdown
## Summary
- <bullet 1>

## Breaking changes        (only if --breaking)
- <note>

## Test plan
- [ ] <step 1>

## Linked                  (only if --spec/--link)
- Spec: [`specs/NNN-…/`](specs/NNN-…/)

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

## 5. Create the PR

```bash
gh pr create \
  --title "$TITLE" \
  --body "$BODY" \
  --assignee "$ASSIGNEE" \
  --label "$LABEL1,$LABEL2" \
  --base "$BASE"
```

Omit `--assignee`/`--label` if the user chose Unassigned/None. If a selected
label doesn't exist in the repo, create it first:

```bash
gh label create "<label>" --color "1d76db"
```

## 6. Confirm

Output the PR URL. If CI is relevant to the change, offer to watch it:
`GH_TOKEN=placeholder gh run watch --exit-status`.
