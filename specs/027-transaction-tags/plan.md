# Implementation Plan: Transaction Tags & Richer Notes

**Branch**: `feat/transaction-tags` (spec dir `specs/027-transaction-tags`) | **Date**: 2026-07-18 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/027-transaction-tags/spec.md`

## Summary

Add free-form, household-scoped **tags** (orthogonal to category) and a per-transaction
**notes** text, then wire tag filtering + notes/tag-name search into the existing Transactions
filter stack. Data lands in a normalized `tags` table + `transaction_tags` join (mirroring the
`household_people` / `transaction_shares` pattern) plus a `notes` column on `transactions`. The
pure `filterTransactions` engine gains a `tags` dimension and richer `matchesQuery`, both extended
in the regression-vector suite. All UI reuses existing calm chip primitives — no new tokens, no
dashboard changes.

## Technical Context

**Language/Version**: TypeScript 5 (strict), React 19, Next.js 16 (static export). SQL for Postgres 17 (Supabase).

**Primary Dependencies**: `@supabase/supabase-js`, Tailwind v4, Vitest 4. No new dependencies.

**Storage**: Supabase Postgres. New: `tags` table, `transaction_tags` join, `transactions.notes` column. All money untouched.

**Testing**: Vitest (`cd web && npm test`), regression vectors in `shared/test-vectors/transaction-filters.json` (generated by `npm run gen:vectors`), `tsc --noEmit`. TDD: failing unit test → implement → refactor; golden vectors extended and re-locked.

**Target Platform**: Web (desktop + responsive) and the Capacitor iOS shell (same bundle). Linux sandbox runs everything JS + local Supabase; no Xcode.

**Project Type**: Single canonical web app + shared Supabase backend (see `docs/index.md`).

**Performance Goals**: No new network round-trips on the hot path beyond two additional bootstrap selects (`tags`, `transaction_tags`) folded into the existing `loadAll` fan-out; filtering stays in-memory and O(n·tags).

**Constraints**: Additive only — a transaction with no tags/notes behaves exactly as today. Filter engine stays pure + deterministic + vector-locked. RLS on every new table. Explicit table grants (spec 024 lesson — new PG17 stacks don't auto-grant DML).

**Scale/Scope**: Household-sized data (hundreds–low-thousands of transactions, tens of tags). One migration, ~2 new domain types, ~6 touched TS modules, ~3 touched components + 1 new tag-editor component.

## Phase 0 — Research

See [research.md](./research.md). Key decisions:

1. **Normalized `tags` table + `transaction_tags` join** (not a `text[]` column) — the spec/backlog explicitly asks for it, and it mirrors the household roster pattern (dedup, reuse, household scope, RLS).
2. **Tag identity = trimmed, case-insensitive name per household** — enforced by a `unique (household_id, lower(btrim(name)))` index + client dedup in `addTag`. No rename/merge UI in v1.
3. **Domain `Transaction.tags` carries tag *ids*** (like `owner_ids`), resolved to names for display/search via a store-held `tags` roster — rename-safe and consistent with the codebase.
4. **`tags` required on `FilterCriteria`, `tagNames` optional on `FilterContext`, `tags?`/`notes?` optional on `Transaction`** — keeps the CLI (`emptyCriteria()` spread) and all existing Transaction fixtures compiling with zero churn.
5. **Optimistic tag creation** — `addTag(name)` returns an existing tag (case-insensitive) or creates one with a client uuid and persists async, matching the app's optimistic-with-rollback pattern.
6. **`writeTags` mirrors `writeShares`** (delete-then-insert join rows) but tags have no sum invariant, so a tag-write failure surfaces an error without rolling back the parent transaction.
