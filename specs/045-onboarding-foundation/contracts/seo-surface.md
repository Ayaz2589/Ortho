# Contract: SEO Surface & Landing Catalogs

**Files**: `web/app/robots.ts`, `web/app/sitemap.ts`, `web/app/layout.tsx` (modified),
`web/lib/i18n/landing/{en,es,bn,ja,zh,ko}.ts`

This is the application's **first indexable surface**. Nothing in the repo publishes crawl rules or a
sitemap today, and `web/public/` still holds the Next.js starter SVGs.

---

## 1. `app/robots.ts`

A static Route Handler — supported under `output: 'export'` (research §1).

```ts
export default function robots(): MetadataRoute.Robots
```

| Rule | Value | Why |
|---|---|---|
| `userAgent` | `*` | |
| `allow` | `/landing/` | The six entry points are the indexable surface (FR-023) |
| `disallow` | `/dashboard`, `/transactions`, `/planning`, `/housing`, `/settings`, `/routines`, `/welcome`, `/sign-in` | Signed-in destinations are not advertised for indexing (FR-023) |
| `sitemap` | `${siteUrl()}/sitemap.xml` | Same origin resolution as everything else (FR-002) |

> `disallow` here is a *crawl-advertising* decision, not a security control. These routes are already
> protected by authentication; listing them keeps crawl budget on the pages that matter and stops
> empty pre-auth shells being indexed as thin content.

## 2. `app/sitemap.ts`

```ts
export default function sitemap(): MetadataRoute.Sitemap
```

Exactly six entries, generated by mapping `landingSlugs()` — never hand-listed (FR-002, SC-006).

Per entry:

| Field | Value |
|---|---|
| `url` | `landingUrl(slug)` |
| `alternates.languages` | All six `locale → landingUrl(slug)`, plus `x-default → landingUrl('en')` |

**Must not include** the root, the sign-in route, or any signed-in destination (FR-022).

`lastModified` is deliberately **omitted**. A build-time `new Date()` would change on every deploy,
making the sitemap churn without the content changing — and it would make the build
non-deterministic, which the repo's testing discipline treats as a defect.

### Invariants (pinned by test)

1. Exactly `landingSlugs().length` entries — adding a locale adds an entry with no edit here.
2. Every URL absolute and origin-consistent with `siteUrl()`.
3. Every entry carries all six alternates plus `x-default`.
4. No signed-in route present.

## 3. `app/layout.tsx` — `metadataBase`

The only change to the root layout:

```ts
export const metadata: Metadata = {
  metadataBase: new URL(siteUrl()),
  title: 'Ortho',
  description: 'Household finance, in order.',
}
```

Documented as belonging in the root layout so URL-based metadata resolves across all routes
(research §2). The existing `title`/`description` and the appearance/text-size boot scripts are
untouched — this feature adds one field and changes no behavior for any existing route.

## 4. Landing catalogs — `lib/i18n/landing/*.ts`

Six small, funnel-only catalogs. **Deliberately separate from the app catalogs**, which are 32–55 KB
each and must never enter a landing page's initial bundle (research §3).

```ts
export interface LandingCatalog {
  /** <title> for this locale's entry point. */
  metaTitle: string
  /** <meta name="description"> for this locale's entry point. */
  metaDescription: string
  /** The one line the placeholder renders. Replaced by 046. */
  placeholderLine: string
}
```

### File shape — reserved regions

Every catalog file carries both reserved regions, empty on delivery (FR-024, FR-025):

```ts
const en: LandingCatalog = {
  metaTitle: 'Ortho — household finance, in order.',
  metaDescription: '…',
  placeholderLine: '…',
}

// --- spec 046 landing copy — insert only between these markers ---
// --- end spec 046 ---

// --- spec 047 tour copy — insert only between these markers ---
// --- end spec 047 ---

export default en
```

The closing marker, blank line, and opening marker give any two insertions at least three lines of
unchanged context — comfortably clear of the adjacency that would force a merge conflict
(research §9).

### Invariants (pinned by `test/i18n/landing-catalogs.test.ts`)

1. One catalog file per registry slug — no more, no fewer.
2. Every catalog exports every `LandingCatalog` key; none empty, none left as the English string in a
   non-English file.
3. Every catalog contains both reserved region marker pairs, correctly ordered and **empty**.
4. No landing catalog imports an app catalog.

> Invariant 2's "not left as English" check is what stops a placeholder shipping as an
> untranslated stub. It mirrors the existing i18n guard tests (`test/i18n/routines-i18n.test.ts`).

## 5. Verification that cannot be unit-tested

`x-default` does not appear in the bundled Next 16.2.9 docs (research §2). Whether it survives into
the built HTML is verified against `web/out/` in quickstart, not assumed. If Next's types reject the
key, the documented fallback is a literal `<link rel="alternate" hreflang="x-default">` in the
landing layout — the contract above is unchanged either way.
