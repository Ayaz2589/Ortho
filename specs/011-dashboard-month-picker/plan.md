# Implementation Plan: Dashboard specific-month picker

**Branch**: `011-dashboard-month-picker` | **Date**: 2026-06-17 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/011-dashboard-month-picker/spec.md`

## Summary

Add absolute specific-month selection to the dashboard on both iOS (canonical) and web (mirror), beside the existing relative range selector (Month/3M/6M/1Y). A month selection resolves to the **already-shared, golden-vectored `monthBounds('YYYY-MM')`** half-open UTC window and feeds the existing interval-driven cards plus Budget and Insights (which already accept a reference date). The selection is a **transient override** of the persisted relative range. The dashboard's time scope is consolidated into one source per surface so mobile/desktop (web) and iOS stay in lockstep, and a small new pure helper — `availableMonths(transactions)` — is added and **golden-vectored** so the two clients derive the same month list. PARITY.md gains one capability row.

## Technical Context

**Language/Version**: TypeScript (web — Next.js 16 App Router + React 19 + Tailwind v4); Swift / SwiftUI (iOS, canonical)

**Primary Dependencies**: None new. Web reuses `lib/transactionFilters.ts` (`monthBounds`), `components/dashboard/range.ts`, `lib/useDashboardRange.ts`, the `Seg`/`RangePicker` UI kit. iOS reuses `TransactionFilters.swift` (`monthBounds`), `DashboardRange.swift`, `AppState`, `DashboardView.swift`.

**Storage**: Supabase (USD cents) — **no schema/migration/config change**. The relative range continues to persist (web `localStorage 'dashboardRange'`, iOS `UserDefaults 'dashboardRange'`); the selected month is **in-memory only**.

**Testing**: web Vitest (`web/test/**`), iOS XCTest (`iOS/Ortho-iOSTests/**`), shared golden vectors (`shared/test-vectors/*.json`) generated by `web/scripts/gen-vectors.ts` and asserted by both suites. Reference dates are injected (never the real clock).

**Target Platform**: iOS app + responsive web (compact 0–639 / medium 640–1023 / expanded 1024+).

**Project Type**: Cross-surface mobile + web product over one Supabase backend; pure finance/date logic mirrored in TS + Swift and locked by golden vectors.

**Performance Goals**: No new per-frame cost; selecting a month re-renders the dashboard cards once (same cost as switching the relative range today).

**Constraints**: Design tokens only; semantic, keyboard-reachable controls with disabled edge states; `prefers-reduced-motion` respected; the chosen-month window standardizes on the **UTC, vectored** `monthBounds` so iOS↔web agree at month edges.

**Scale/Scope**: 2 surfaces; 1 new pure shared helper (`availableMonths`, vectored); scope-resolution glue; 1 new UI control per surface (stepper + month list); 6 cards rescoped (4 already interval-driven, 2 — Budget, Insights — rewired to a reference date); 1 new vector file; 1 PARITY.md row; new web + iOS tests.

**Structure decision**: No new project or module. Extend the existing paired dashboard-scope modules (`range.ts` ↔ `DashboardRange.swift`) with `availableMonths` + scope resolution, add one new UI control per surface, and rewire the two current-month-hardcoded cards to a reference date. The web mobile/desktop scope is hoisted into the existing `useDashboardRange` hook (a scope hook) so both layouts read one source.

## Phase 0 — Research

See [research.md](./research.md). All spec unknowns were resolved during brainstorming/exploration; research records the load-bearing decisions: reuse the vectored `monthBounds` for the selected-month window; derive the month key by **string-slicing the stored ISO date** (both surfaces) so the month list matches; feed Budget/Insights a **mid-month (15th, noon UTC) reference date** so local-vs-UTC calendar math lands on the selected month; selected month is **transient**; new `availableMonths` is **golden-vectored**.
