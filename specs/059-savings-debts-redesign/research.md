# Research: Savings & Debts — replacing the Goals section

**Feature**: `specs/059-savings-debts-redesign` | **Date**: 2026-09-01

Every question below was raised by the Technical Context or by a `NEEDS CLARIFICATION` in the first
pass of `plan.md`. All are resolved; none remain open.

---

## R1 — Where does the projection engine live, and can it touch `goals.ts`?

**Decision**: A new pure module, `web/lib/finance/goalProjection.ts`. `web/lib/finance/goals.ts` is
**not modified**.

**Rationale**: `goals.ts` exports `goalProgress` and `goalPacing`, and both are pinned by
`shared/test-vectors/goals.json` (generated by `web/scripts/gen-vectors.ts:559`, regenerated and
diffed in CI). Any behavioural edit there is vector drift on a contract three other surfaces already
consume (`GoalsBody`, `GoalsPanel`, `planSummary.ts`). The redesign needs *different* derivations —
cadence, on-plan classification, pace basis, finish date — not different progress arithmetic. Adding
a sibling module keeps `npm run gen:vectors && git diff --exit-code` byte-identical throughout, which
is the same guarantee spec 057 US4 gave itself.

**Precedent**: The spending-pace redesign (PR #126) faced exactly this and answered it the same way —
`lib/finance/spendingPace.ts` was created new rather than reshaping the engine the old panel used.

**Alternatives considered**:
- *Extend `goals.ts` with new exports.* Rejected: it drags the vectored module into the blast radius
  of every future edit for no gain, and `goalPacing`'s target-date-driven model is conceptually the
  opposite of the new contribution-driven one — co-locating them invites one being used where the
  other was meant.
- *Reshape `goalPacing` to the new model and re-baseline the vectors.* Rejected outright: it changes a
  regression lock to make new code convenient, and the old model is still correct for the dated-goal
  "off-track insight" that ships on the dashboard.

**Consequence**: `goalPacing`'s off-track insight keeps working unchanged, and the two models coexist.
The plan notes this explicitly so a later reader does not "unify" them by accident.

## R2 — How is the cadence amount derived when contributions are not identical?

**Decision**: The **modal** (most frequent) amount, with ties broken by the **larger** amount, and by
recency only if still tied. The modal day-of-month is derived the same way, ties broken by the
**earlier** day.

**Rationale**: The handoff specifies "the modal (most frequent) contribution amount" but not the tie
rule, and a tie is common in practice (two contributions of $600, two of $650). Breaking toward the
larger amount makes the projected finish date *later*, never optimistically early — the conservative
direction, and the one that cannot mislead a member into thinking a debt clears sooner than it will.
The day tie-breaks earlier for the same reason: an earlier cadence day never claims a payment landed
later than it did.

**Alternatives considered**:
- *Mean of all contributions.* Rejected: one atypical catch-up payment drags the cadence away from
  the amount the member actually pays every month, which is the number the sub-line prints.
- *Most recent amount.* Rejected: a single wrong entry becomes the cadence for the whole card.
- *Median.* Rejected: for an even count it invents an amount no contribution ever had, which then gets
  printed as "$625/mo since Jan" — a figure the ledger cannot justify.

## R3 — What is the on-plan tolerance, and where does it live?

**Decision**: ±2% of the cadence amount, with a floor of 1 cent, declared in a new
`GOAL_PROJECTION_THRESHOLDS` constant beside the engine.

**Rationale**: The handoff states ±2% directly. The 1-cent floor mirrors the existing
`goals-thresholds.ts` reasoning — without it, a cadence small enough that 2% rounds to zero would make
every contribution off-plan by rounding alone. Naming the cutoffs in one labelled object is the
established repo idiom (`INSIGHT_THRESHOLDS`, `GOAL_THRESHOLDS`); tuning the rule then means editing
one named field, not a bare number mid-function.

**Alternatives considered**: A hardcoded `0.02` inline — rejected as inconsistent with two existing
threshold modules and impossible to find later.

## R4 — How are the four charts built: recharts, or hand-drawn?

**Decision**: Split by shape.
- **Progress toward target** (cumulative + target line + dashed projection) → **recharts**, in a new
  `components/goals/charts/GoalProgressChart.tsx`, loaded through `next/dynamic`.
- **Pace against plan** (bars + plan line), **consistency** (month cells), the **card track**, and the
  **aggregate split bar** → plain CSS/flex, no charting library.

**Rationale**: The bundle guard `test/bundle/no-eager-recharts.test.ts` forbids reaching recharts
except via `next/dynamic`, so anything using it pays a dynamic-import boundary. That cost is worth it
for a true continuous line chart with two series and a projection segment, and absurd for four
absolutely-positioned divs. The existing `PaceRaceChart` (spec 057 US4) is the precedent for the
former; `CycleStrip`/`SpendHeatmap` are the precedent for the latter. The handoff itself draws the
pace bars and consistency cells as plain divs with heights and opacities.

**Alternatives considered**:
- *All four in recharts.* Rejected: the consistency strip has no axes, no scale, and no continuity —
  it is a row of coloured cells. Modelling it as a chart adds a dynamic chunk and a ResponsiveContainer
  to render seven rounded rectangles.
- *All four hand-drawn in SVG.* Rejected for the progress chart only: it needs a responsive width, and
  hand-rolling the viewBox math duplicates what `ResponsiveContainer` already solves everywhere else
  in this app.

**Constraint carried forward**: the prototype's `<path>` coordinates are a static mock. The plan
requires the chart be built from the data with the described *geometry* (x-span = start → projected
finish), never by transcribing the mock's path — the handoff says so explicitly under Fidelity.

## R5 — How far does the "Savings & Debts" rename actually reach?

**Decision**: Seven member-facing strings change meaning, across six languages. English is the
identity catalog (source strings are the keys), so a rename is a **key change** in
`lib/i18n/{bn,es,ja,ko,zh}.ts` plus every call site.

**Surface inventory** (measured, not estimated):

| Current string | Where | Becomes |
|---|---|---|
| `Goals` | `GoalsSummaryCard.tsx:65` (section title) | `Savings & Debts` |
| `Goals` | `lib/widgets/registry.tsx:111` (widget title) | `Savings & Debts` |
| `Progress toward your savings goals.` | `registry.tsx:112` (widget description) | rewritten for both kinds |
| `New goal` | `GoalsSummaryCard.tsx:59`, `GoalForm.tsx:89` | `New item` |
| `Edit goal` / `Delete goal` | `GoalForm.tsx` | `Edit` / `Delete` phrasing without "goal" |
| `No goals yet — create one to start saving toward it.` | `GoalsSummaryCard.tsx:68` | rewritten for both kinds |
| `No goals yet.` | `GoalsBody.tsx:24`, `GoalsPanel.tsx:67` | rewritten |

**Rationale**: `registry.tsx`'s `title`/`description` are raw English strings translated at render, so
the widget rename is a one-line change plus catalog keys — no registry restructuring. Note the widget
`id` stays `'goals'`: it is the **localStorage key** for per-browser widget enablement, so changing it
would silently reset every existing user's dashboard layout. That is a real user-visible regression
hiding behind a cosmetic rename, and the plan pins it with a test.

**Alternatives considered**: Renaming the widget `id` and route for tidiness — rejected for the
localStorage reason above, and because `/planning/goals?id=` URLs are already in the wild and in the
spec-057 panel's `href`.

## R6 — Does the dashboard widget body get the full treatment?

**Decision**: No. It adopts vocabulary, headline-by-type, and bar direction; it does **not** get the
aggregate header, the ETA line, the disclosure, or any chart.

**Rationale**: The widget body renders inside a fixed, uniform grid cell — the card is "a GLANCE, one
number", per the spec-057 framing that the whole widget board is built on. Constitution II forbids
shrinking type or stretching rows to fit more data. The handoff never drew the widget, so anything
beyond the vocabulary is invention; the panel behind it is where the depth belongs, and that panel is
in scope.

**Alternatives considered**: Putting the ETA line in the widget body — rejected: at three goals it
overflows the cell, and the failure mode is the exact horizontal/vertical overflow class that
`fix/058-mobile-horizontal-scroll` is currently fixing on another branch.

## R7 — How does the card's disclosure animate without violating the motion rules?

**Decision**: Animate `height` (via a measured `grid-template-rows: 0fr → 1fr` transition) at
`--duration-fast` / `--ease-out`, and let the existing global `prefers-reduced-motion` block drop it to
instant.

**Rationale**: `app/globals.css:264` and `:619` already reduce motion globally for transitions and
drawer animations, so honouring Principle V costs nothing new if the disclosure uses the same tokens
rather than a bespoke duration. The `0fr → 1fr` grid technique animates to *content height* without
JavaScript measurement, which matters because the row count varies from 1 to 12.

**Alternatives considered**:
- *No animation.* Rejected: the handoff calls out that expanding must not shift the cards below it
  abruptly — that abruptness is the thing being avoided.
- *`max-height` transition to a guessed maximum.* Rejected: the classic bug — the easing is wrong for
  any list shorter than the guess, and it clips any list longer than it.

## R8 — Only one card expanded at a time: whose state is that?

**Decision**: The section owns a single `expandedId: string | null`; the card is controlled.

**Rationale**: "At most one open" is a statement about the *set*, so it cannot live in each card's
local state without cards reaching into each other. This also makes the behaviour trivially testable:
expand A, expand B, assert A's rows are gone.

**Alternatives considered**: Per-card local state plus a broadcast on open — rejected as the same
state, hidden, with an ordering bug waiting in it.

---

## R9 — Is there a person/household scope question here?

**Decision**: Out of scope; this feature renders the household's items, exactly as all four surfaces do
today.

**Rationale**: The spec-057 follow-up brief explicitly recorded "whether goals should be person-scoped
is a separate open question this panel does not settle", and spec 056 deliberately left `goals`
unscoped pending its own PR. Answering it here would silently change what the dashboard shows under a
person scope — a behaviour change well outside a redesign, and one that belongs with the 056 follow-up
that owns the question.

## R10 — What is the reference-date discipline?

**Decision**: Every derivation takes an injected `now: Date`. The Planning page and detail page pass a
`useMemo`'d `new Date()`; the dashboard surfaces pass the scope context's `now`, as they already do.

**Rationale**: Constitution VI requires injected reference dates. It is also the only way SC-006 —
that the card, the detail page, the widget, and the panel state *identical* projections for the same
item — is testable at all: with an ambient clock, four surfaces can straddle midnight and disagree
legitimately.

**Additional care**: month arithmetic must use local-calendar getters, matching the `dayIndex` rule
already in `goals.ts` and `goalSeries.ts`, or a projected finish month flips west of UTC. The repo has
a dedicated timezone suite (`npm run test:tz`, and `test/finance/goal-series-timezone.tz.test.ts` is
the existing example for exactly this module family) — the new engine gets one too.
