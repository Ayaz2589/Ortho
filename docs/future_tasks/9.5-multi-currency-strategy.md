# 9.5 Multi-currency accounting strategy

- **Section:** 9. Commercial readiness
- **Priority:** 🟡 medium — a **decision** with a large implementation tail
- **Track:** B (product) — research-gated (is an international audience in scope?)

- **What:** Decide whether Ortho stays **USD-accounting-with-display-conversion**
  or moves to a **native-currency ledger** for international households.
- **How it works today:** every amount is stored as USD cents at the rate-at-entry,
  then converted for display via the currency layer. Consequence: for a non-USD
  household, historical totals **shift as FX moves** ("why did my March groceries
  change?"), and there is no true multi-currency ledger — the stored figure is a
  USD snapshot, not the native amount.
- **The decision:** either (a) **scope launch to US / USD** and defer this, or
  (b) commit to storing native-currency amounts (a real multi-currency model) so
  historical figures are stable in the user's own currency. Don't ship the silent
  in-between.
- **Ortho fit:** "commercial" implies arbitrary locale/currency. The choice gates
  a chunk of the money layer, so make it **before** hardening the rest — the answer
  changes what "correct" means for every stored amount.
- **Cost:** the *decision* is cheap; option (b)'s *implementation* is large (schema,
  migration, every read/write, the vector harness).

> Source: the commercial-readiness & sequencing review (2026-07-17). Note: this is
> about the *accounting model* (single-currency ledger), not the FX feed — a live
> rate source already exists.
